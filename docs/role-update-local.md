# 行业 AI 岗位组合与本地核验

Agent Ops 使用一套共享底座，但岗位按行业与交付物设计，不照搬传统部门设置。Router 先判断真正要交付什么，再选择完成它所需的最少能力；有明确的多项交付时，按技能输入/输出依赖串联，并去掉重复步骤。

执行职责可以合并。例如软件工作可把已登记的前端与后端实现能力组合为一个“软件实现”AI 岗位；内容行业也可将有明确先后关系、分属不同源岗位的策划与视觉制作能力组合。只有至少合并两个同业源岗位、确实减少岗位数时才应用组合。不同交付物仍各自保留技能契约和路由样例，因此一句需求只触发相关能力。独立测试/复核不能与自己产出结果的能力合并，发布、部署等高风险批准始终由人作决定。

用户提出岗位名称或组合建议后，Codex 先调用 `list_registered_roles` 查看行业、职责、能力和产出，再为每个源技能提供具体别名及至少两个正向路由例子；还需提供至少两个反向例子。随后调用 `reconcile_role_suggestion`。后台确认所有技能已登记且属于同一行业、源岗位数确实减少、输出不重复、别名不跨行业抢路由、各正例能命中对应技能、反例不命中新岗位，并拒绝把产出与独立复核合并。

通过后，本机 SQLite 保存一个岗位组合、复用已有技能契约的本地副本、按技能隔离的路由规则和核验记录。没有新代码能力、工具权限或模型调用。`role_updates_status` 查看记录，`revoke_role_update` 撤销并保留审计事件。服务重启后会恢复已应用组合。

验证是结构和样例路由核验，不等同于行业专家认证或工作质量证明。跨行业建议、未登记能力、技能别名冲突或缺少独立复核时，后台拒绝自动应用；Codex 应说明缺口，不能伪称已激活。

## MCP 操作顺序

1. 用户提出岗位增补、合并或叫法调整后，先查询 `list_registered_roles`。
2. 按具体交付物选最少的已登记技能；按每个技能提供别名、正例及公共反例。保留独立审核、测试与批准边界。
3. 调用 `reconcile_role_suggestion`。只有 `status=applied` 才代表本机路由已更新；失败时不改动注册表。
4. 使用 `route_task` 核验真实任务分配，并按 `host_execution.steps` 的技能依赖顺序由 Codex 执行。不要调用 `run_task`。

所有建议及样例只写入本机，不发送模型或 GitHub。岗位职责变化时可撤销旧组合，再提交新的、有证据的组合。
